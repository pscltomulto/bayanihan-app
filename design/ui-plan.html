Bayanihan app — UI plan

A mobile-first PWA, designed on the web first. Repo bayanihan-app, separate from the API. Draft for owner review, 2026-11-23.

Goal

Design every screen of the user app as reviewable HTML before writing app code, so the build (U10 onward) only has to turn approved mockups into components that call the existing API.

Done when: all U0–U9 mockups are approved in Lavish, the core loop is clickable end to end, and every screen and state is mapped to its API endpoint and error codes.

The loop the app must make easy

Approach

  • One self-contained HTML file per phase in design/: inline CSS and JS, fake Dumaguete data, no real personal data.
  • UX skill + design agent: ux-designer uses the uix skill (design system + 10-point checklist) and always proposes first: a Lavish page with the critique and numbered before/after pairs or options. You decide each item; only approved items are applied.
  • Reviewed in Lavish; each comment applied and answered until you approve. Nothing moves to the next phase without approval.
  • KokonutUI / shadcn look: same tokens, spacing and component shapes, so each mockup piece maps to a real component later.
  • Mobile first at 360–430 px, checked at 768 px and desktop; 44 px touch targets; safe areas for the installed app.
  • Every state drawn: loading, empty, error, offline, and the API's refusals (409, 422, 429 with a retry time).
  • Each screen lists its endpoints from openapi.yaml; anything the API can't do goes on an API gaps list instead of being faked.

Phases

U0

Design foundation and PWA shell

Tokens (light and dark), core components, bottom-nav shell, install prompt, offline banner, update prompt, shared loading/empty/error/429/409 states.

U1

Sign-in and verification

Phone + OTP, profile to tier 1, tier explainer and caps, ID + selfie for tier 2, pending/approved/rejected, re-verification and dormant-review notices.

U2

Browse and task detail

Feed as list and map (approximate locations only), search and filters, task detail for non-parties, fee preview.

U3

Post a task

Form with pin and photos, fee and escrow breakdown, tier caps, not enough points, and every can_post blocked reason.

U4

Applying and choosing a worker

Apply, my applications, applicant list with ratings and standing, pick one, withdraw and cancel.

U5

Doing the work and chat

Assigned view (exact pin only for the two parties), start, photo proof, confirm, cancel request, auto-release countdown, chat with images.

U6

Ratings, disputes and reports

Two-way rating, opening a dispute with evidence, its status and decision, reporting a user or task.

U7

Wallet

Available and locked balance, history, cash-in (fake gateway), cash-out states including held and refunded, payout accounts with masked numbers.

U8

Notifications, profile and settings

Notification list and push permission, profile edit, skills, public profiles, standing, devices and sign-out everywhere, English/Filipino.

U9

Clickable prototype and handoff

Core loop linked end to end, accessibility pass, screen → endpoint → error-code table, API gaps list.

U10

Stack decision (you)

Pick the PWA stack and hosting (KokonutUI points to React + Tailwind + shadcn/ui), then plan the build phases.

Open questions

1. When to update the API spec?

spec.md still says Flutter Android and "web app: Not in V1".

Now (recommended) — edit spec §1 and §8 to say PWA, so both repos agree before design starts.
At U10 — change it once the stack is picked.

2. How are mockups styled?

The repo rule is self-contained HTML with no CDN.

Hand-written CSS with shadcn tokens (recommended) — works offline and anywhere, no external scripts.
Tailwind browser runtime from a CDN — closer to KokonutUI's class names, but needs the network and breaks the no-CDN rule.

3. Which language to design in first?

The spec wants English and Filipino.

English first, Filipino in U8 (recommended) — leave room for longer strings throughout.
Both from U0 — every mockup has a language toggle.

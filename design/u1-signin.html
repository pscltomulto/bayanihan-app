Sign-in and verification

Phone sign-in, consent, profile setup to tier 1, the tier explainer, ID verification to tier 2, and the return notices, built from the owner's answers on the U1 proposal. Uses only U0 tokens and components. Every screen lists its endpoints. Fake Dumaguete data only; the phone number shown is the user's own, as /me returns it.

Decisions applied

The owner accepted every recommendation in design/proposals/u1-signin-proposal.html. Nothing was left out.

  1. 1Onboarding order: C · Offer setup right after sign-in, with "Look around first"; setup card on Browse until tier 1 (recommended)
  2. 2Code input: B · One field with autocomplete="one-time-code", auto-submit at 6 digits (recommended)
  3. 3Consent: B · "Before you start" screen for new accounts only, plus a privacy line on the phone screen; separate ID consent at the ID step (recommended)
  4. 4Profile layout: A · One page with progress; reused as Edit profile in U8 (recommended)
  5. 5Name: A · Real name as on the ID, with the hint that neighbors see it (recommended)
  6. 6Barangay: A · Searchable list, no location prompt (recommended)
  7. 7Skills: C · Optional, on the "you can now post" screen (recommended)
  8. 8Tier explainer: C · Progress card on Me plus a full explainer screen (recommended)
  9. 9ID and selfie capture: C · Camera with frame guide, upload fallback; selfie 9.2 A · front camera with oval and tips (recommended)
  10. 10Verification status: B · Card on Me, detail screen from the card and the notification; rejected flow as drawn (recommended)
  11. 11Re-verify and dormant notices: B · Sheet once on return, card on Me, U0 blocked screens when needed (recommended)
  12. 12Language: B · Toggle on the welcome screen, saved after sign-in (recommended)

Skills asked on the success screen, optional (decision 7). Categories need a list endpoint (API gap).

Verify your ID: intro

ID photo

Camera with frame guide, upload as fallback (decision 9). On desktop the upload path opens directly.

Selfie

Front camera, oval guide and three tips, no gallery on phones (decision 9.2). Desktop and a blocked camera fall back to upload.

Check and send

Both photos made smaller on the phone, then sent in one multipart request (up to 8 MB each).

15

ID check detail

Opened from the Me card or the "ID verified" / "ID not approved" notification (decision 10). Each reason has its own fix.

16

Coming back: sheets and blocked screens

Decision 11: a sheet once on return, the card on Me (section 9), and the U0 blocked screens unchanged when posting (U0 §6) or cashing out (U7). A tier-1 account stamped for re-verification still posts and gets no sheet.

17

Session expired

Any 401 sends the user to the phone screen with the number kept on the device.

18

Widths: 430, 768 and desktop

Sign-in screens keep a 480 px column on tablets; desktop splits brand and form. No bottom nav before sign-in.

API gaps

Backend work. The screens above mark where they depend on these.

  1. No barangay list.PATCH /me needs a barangay key, but nothing returns the active barangays (key, name). Needed for decision 6 and reused by U2 filters and U3 posting.
  2. No category list.PUT /me/skills needs category keys with labels in the user's language. Needed for decision 7 and U2 filters. (U0 noted the icon mapping, not the missing list.)
  3. Consent is not recorded.Nothing stores which Terms and Privacy notice version a user accepted, or when. Needs e.g. POST /me/consents or fields on PATCH /me (terms_version, privacy_version, accepted time), and /me saying whether a newer version must be accepted.
  4. No separate ID and selfie consent.POST /me/verification takes no consent flag; sensitive personal information needs its own recorded consent at submission.
  5. Tier caps and retention are not readable.The explainer and copy quote the tier caps (₱1,000 / ₱5,000, "starting values to tune") and the ID image deletion time (timers.id_image_purge_days, 30–365). /tasks/quote gives only the user's own cap. A small public settings response would keep copy true when the owner changes them.
  6. Rejection "other" and "underage" give no next step.other has no note the user can act on; an optional reviewer note visible to the user would help. For underage, the API does not say whether a new check is allowed (the notice text omits "send again"); a can_resubmit flag on GET /me/verification would let the app hide the button correctly.
  7. "Live selfie" is not enforced.The API accepts any image as the selfie; the app can only steer people to the camera. Liveness, if wanted, is a backend or provider decision.
  8. Still open from decision 0002:every 429 needs a retry time the browser can read (Retry-After exposed through CORS, or errors.retry_after); the phone, code and send screens show "Try again in" only with it.

Applying and choosing a worker

Both sides of an open task: a neighbor applies with a note, start time, past work and an optional distance band; the poster compares full cards, stars up to 5, asks up to 3 questions and picks one, seeing exactly what happens before confirming. Exits (withdraw, drop out, close, cancel) and reminders included. Built from the owner’s answers on the U4 proposal with U0–U3 tokens and components. Every frame lists its endpoint. Fake Dumaguete data; nobody’s standing, phone or exact location is shown to anyone else.

Standing stays private

The list arrives ordered with better standing first; nothing shows, names or hints at another person’s standing. A person’s own standing appears only in their own drop-out and cancel dialogs, marked “only you see it”.

What others see

Only what each endpoint returns to that viewer: display name, photo, ID verified, rating, tasks done, jobs in this category, distance band, start, note, past work. No phone, legal name, birth date, ID images or exact pin.

Money

Nothing moves on apply or pick. Amounts are “400 pts · ₱400”; the pick sheet shows held, fee and received; a cancel before the pick returns everything.

API gaps

Backend work; the mockup will draw around them and mark the missing data. Still open and reused here: a readable 429 retry time (0002), and applicants can’t tell a full task from a closed one (0004).

  1. 1. The poster can’t tell whether cancelling will cost standing. Spec §6 makes an early cancel free only when every waiting applicant applied less than an hour ago and nobody was starred or messaged, but the poster’s task view returns nothing that says which case applies, so the dialog can only say “can lower”. Suggest cancel_lowers_standing (bool) or free_cancel_until on the poster’s GET /tasks/{ulid}.
  2. 2. My applications rows are too thin, and closed tasks can’t be opened. The applicant’s task block has only ulid, title, points, deadline_at: no task status, category (for the icon tile), barangay, worker_receives, applicant_count or poster. Once the task is no longer open, GET /tasks/{ulid} returns 404 to a non-picked applicant, so the row can’t open anything. Suggest those fields in the applicant’s view of the application.
  3. 3. “expired” means three different things to the applicant. An application becomes expired when the deadline passes, when the poster cancels and when staff remove the task. The app can’t word it (“The poster cancelled” vs “No one was picked in time”). Suggest a closed_reason on the applicant’s view (or the task’s cancel_reason in its block).
  4. 4. No unread signal for questions. Rows carry only poster_questions / worker_questions counts, so neither side can mark “new question” on a card or in My applications; the question_received notice is the only cue. Suggest last_question_from and last_question_at (or an unread count) on both views.
  5. 5. Pick reminders aren’t machine-readable. Both reminders use kind pick_reminder with text only; the app can’t tell “24 h after the first applicant” from “6 h before the deadline” to style it or deep-link. Suggest data.reason = applicants_waiting | deadline_soon. Minor.
  6. 6. Apply and application docs are incomplete. openapi.yaml for POST /tasks/{task_ulid}/applications leaves out refusals the code throws: 403 TIER_TOO_LOW, ACCOUNT_SUSPENDED / ACCOUNT_CLOSED, 409 TASK_UNDER_REVIEW, INVALID_TRANSITION, APPLICATIONS_CLOSED with reason accepted, and the two 422 earliest_start_at messages (before today, not before the deadline). GET /applications/{ulid} has no 200 example for either view. Docs only.

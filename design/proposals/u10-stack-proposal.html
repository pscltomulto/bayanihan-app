Building blocks

1–3: what the app is written in and how it installs

1

UI framework

The toolkit every screen is written in. The biggest choice; most others follow from it.

You planned to use KokonutUI (0001). Checked today: MIT licence, active (last change 26 Nov 2026, about 2,400 stars), 116 components. It is React-only: each component is React + Tailwind CSS + Motion + Lucide, copied into the codebase with the shadcn command-line tool. The components sampled use no Next.js-only code, so they run in a plain React app. The admin console in the API repo is Vue 3, so any React choice means two frameworks across the two repos.

A

React 19 + Vite 8, with shadcn/ui and KokonutUI as they are

Recommended
  • Uses KokonutUI and shadcn/ui directly; the mockups were drawn to map onto them one to one
  • Same build tool (Vite) and same styling (Tailwind CSS 4) as the admin, so the tokens carry over
  • The largest pool of developers and examples if you hire help later
  • Two frameworks to know: React here, Vue in the admin
  • Copied components are ours to update; no automatic upgrades
B

Vue 3 + Vite, with shadcn-vue, KokonutUI rebuilt by hand

  • One framework across app and admin
  • shadcn-vue is MIT and well kept (about 10,900 stars, updated this week)
  • No KokonutUI for Vue: every KokonutUI piece the mockups use is rebuilt and maintained by us
  • Look and motion may drift from what you approved
C

Next.js 16 (React) or Nuxt 4 (Vue)

  • Batteries included: routing, server rendering, image tools
  • Next.js keeps KokonutUI as is
  • Built around a Node server we don’t need (see decision 2), so one more thing to run and patch
  • Offline and service-worker setup is harder than in a plain Vite app

Why A: you chose KokonutUI and the designs mirror it. React with Vite gets it without a server, and the Vue admin is a separate surface staff use, so the split costs little. SvelteKit isn’t offered: no KokonutUI, a third framework, no gain for this app.

2

Rendering: phone builds the page, or a server does

Whether pages are assembled on the phone (a single-page app) or on a server first.

Server rendering mainly helps search engines and the first paint of public pages. Almost everything in Bayanihan is behind sign-in, and the task pages show private data, so search engines shouldn’t index them anyway.

A

Single-page app, built to plain files

Recommended
  • No server code to run: the app is a folder of files any web server can hand out
  • The offline shell is simple: cache the files once and the app opens without signal
  • Cheapest to host
  • The very first visit downloads the app before anything shows (kept small with code splitting; later opens come from the cache)
B

Server rendering (Next.js or Nuxt)

  • Slightly faster first screen on a slow phone
  • A Node server to host, monitor and keep patched
  • The server would need the user’s sign-in too, which complicates decision 4
C

Single-page app plus a few pre-built public pages

  • A landing page and the terms or privacy pages show without the app
  • Little to gain today: there is no public landing page in the approved designs
  • Can be added later without changing anything else

Why A: behind a sign-in, server rendering costs a server and buys almost nothing. C can be added later if you want a marketing page.

3

Offline shell, install and updates

The part that makes it a PWA: works on a weak signal, installs to the home screen, updates cleanly.

The designs need an app icon and splash, an install sheet after the first success plus a row in Me, an offline banner, and “needs signal” messages (0002 items 10.1–10.3). A service worker is the small background script that caches the app so it opens offline.

A

vite-plugin-pwa (Workbox inside), “update ready” prompt

Recommended
  • Generates the manifest, icons and service worker from one config; supports React and Vite 8
  • Built-in “a new version is ready, reload” prompt, so nobody is stuck on an old version mid-task
  • Caches the app shell only; API answers are never served stale for money or status
  • One more build plugin to keep updated
B

Hand-written service worker

  • No package; full control
  • Cache versioning and update handling are easy to get wrong, and a broken service worker can trap users on an old app
C

Workbox directly, no plugin

  • Same engine as A, wired by hand
  • More setup for the same result

iPhone limits, whatever we pick

  • No install button on iPhone: Safari never offers the install event, so the install sheet shows “Share → Add to Home Screen” steps there and a real button on Android.
  • Web push on iPhone works only after the app is added to the Home Screen (iOS 16.4 or later) and only after a tap. That matches 0002 item 10.4 (push only from Notifications in Me); push itself waits for gap R1.
  • Safari may clear saved data from sites not opened for about 7 days; the installed app is treated better. So drafts kept on the phone (the U3 draft, the U7 unfinished cash-in) are a convenience, never the only copy of anything that matters.
  • No background sync on iPhone, so retries happen while the app is open (decision 5).

Why A: it is the standard Vite way to do exactly what the U0 PWA pieces need, including the update prompt that keeps someone mid-task on a working version.

Talking to the API

4–5: sign-in, data, live chat and weak signal

4

How the browser stays signed in

Gap P1 (blocks the pilot). Decides the domain layout too.

Today the API signs people in with a token made for a phone app (POST auth/otp/verify returns it; it never expires). A web page can only keep such a token in browser storage, where any script that sneaks into the page (an XSS bug, a bad package) can read and steal it. Laravel’s own docs say not to use these tokens for your own web app and to use cookie sign-in instead. Checked in the API: cookie sign-in isn’t switched on (no statefulApi()), CORS uses Laravel’s default (any site, no cookies, no readable Retry-After), and Reverb accepts any origin.

A

Cookie sign-in (Sanctum SPA) on app.example.ph + api.example.ph

Recommended
  • The sign-in lives in a cookie page scripts can’t read, so an XSS bug can’t walk off with the account
  • Built into Sanctum, which the API already uses; chat sign-in (/api/broadcasting/auth) already runs through auth:sanctum
  • Tokens stay available for a native app later
  • Needs CSRF protection (a second cookie and header), which Sanctum provides
  • API work in I1: start a session on OTP verify, end it on sign-out and “Sign out everywhere”, and keep phones signed in for weeks, not the 2-hour default
  • The cookie scope must be set so the admin console’s session isn’t widened to the app’s address
B

Keep the token, stored in the browser

  • No sign-in change in the API; only CORS and a narrowed origin list
  • App and API can live on any domains
  • A token that never expires sits where scripts can read it; one XSS bug or bad package means stolen accounts with money in them
  • Against Laravel’s guidance for first-party web apps
C

Cookie sign-in, app and API on one address

  • Same cookie protection as A, and no CORS at all: app.example.ph/api is passed through to Laravel
  • No shared parent-domain cookie to scope
  • The web server must also pass through Reverb’s live connection and broadcasting sign-in
  • Ties the app’s hosting to the API server (rules out a CDN host in decision 9)

Why A: real money sits behind each account, so the sign-in belongs in a cookie scripts can’t touch, which is what Laravel recommends. Two subdomains under one domain is the standard Sanctum layout. C is a good fallback if scoping the cookie turns out awkward.

5

Data, live chat and a weak signal

How screens load and refresh data, how chat updates live, and what happens when the signal drops.

The designs ask for: loading, empty, error and offline states on every screen; money actions retried by hand with the same Idempotency-Key and never posted automatically (U3 item 11, U7 item 12); one draft kept on the phone; live chat on the private channel task.{ulid}.{worker_ulid}. Reverb speaks the Pusher protocol, so the browser uses Laravel Echo with pusher-js.

A

TanStack Query + Laravel Echo, retries by hand

Recommended
  • TanStack Query handles loading, caching, refetch on reconnect and paging (the API uses cursor pages) with little code
  • Its offline mode pauses requests and resumes them when signal returns, matching the offline banner
  • A money action makes its key once (when the review screen opens, as U3 says) and reuses it on “Try again”, so a retry can’t pay twice
  • Two packages to learn (Query, Echo + pusher-js)
B

Plain fetch and our own small cache

  • Fewest packages
  • We rewrite caching, refetch-on-focus, paging and offline pause, and get the edge cases wrong at first
C

Offline-first: a local database that syncs

  • Browsing works fully offline
  • Wrong fit: status and money must come from the server, and the designs say “needs signal” rather than queue actions
  • No background sync on iPhone anyway

Why A: it gives every screen the states the designs drew with the least code, and the retry rule stays explicit: same key, user taps, no silent re-posting.

Features

6–7: language, forms, maps and photos

6

English and Filipino, forms and validation

Two small choices answered together.

Every string must exist in English and Filipino with room for longer Filipino text (spec, 0010). Forms show the API’s 422 field errors inline (U0). The server is always the judge; checks on the phone only save a round trip.

A

i18next + react-i18next; React Hook Form + Zod

Recommended
  • i18next: one file per language, plurals (“1 applicant / 3 applicants”), language switch from Me without reload
  • React Hook Form + Zod: quick forms on cheap phones; the API’s 422 errors map straight onto fields
  • shadcn/ui’s Form component is built on React Hook Form
  • Five packages for two jobs
B

Our own string lookup; plain HTML forms

  • No packages
  • Filipino plurals, number formatting and missing-string checks are written by hand
  • More code on long forms (post a task, profile, cash-out)

Why A: both are the common, MIT-licensed defaults for React and match how shadcn/ui forms are built, so the mockups’ form pieces map straight across.

7

Maps and photo compression

Gaps R2 and R3. The spec planned the Google Maps SDK for Android, which a web app can’t use.

The map only ever shows approximate areas (the exact pin is private), as a small strip on Browse and a map view. Photos must shrink to about 300 KB on the phone before upload (spec).

7a · Map

A

MapLibre GL with OpenFreeMap tiles

Recommended
  • MapLibre is free and open (BSD); OpenFreeMap tiles are free with no key and allow commercial use
  • Vector maps can be restyled to the teal and dark theme
  • MapLibre is the largest package here; loaded only on map screens
  • A free public tile service has no guarantee; MapTiler or self-hosted tiles are the paid fallback
B

Google Maps JavaScript API

  • Familiar look; what the spec had in mind
  • Needs a billing account and an API key; pay per map load past the free allowance
C

Leaflet with openstreetmap.org tiles

  • Small and simple
  • OpenStreetMap’s own tile servers don’t allow heavy app use, so we would need a tile provider anyway
  • Leaflet’s last release was 2023

7b · Photo compression

A

The browser’s own canvas, about 40 lines of our code

Recommended
  • No package: resize to a long edge, save as JPEG/WebP, step quality down until under 300 KB
  • Strips location data from the photo as a side effect, which suits the privacy rules
  • Ours to test on old Android phones and iPhone photos
B

browser-image-compression package

  • Ready-made, MIT
  • Last release March 2023; an unmaintained package in the upload path

Why A and A: approximate-area maps need nothing Google-specific, and free tiles keep the pilot at no map cost. Compression is a small job the browser does natively, so no package is worth adding.

Quality and running it

8–9: testing, hosting, deploy

8

Testing, quality checks and TypeScript

How we prove each screen works before you see it, and keep it working.

TypeScript is JavaScript with labelled data shapes, so a typo in a field name is caught before it reaches a phone. KokonutUI and shadcn/ui are written in it. Checked today: TypeScript 7 is out, but the lint tool (typescript-eslint) supports only up to 6.0, and the accessibility lint rules don’t yet list ESLint 10, so the plan pins TypeScript 6.0 and ESLint 9.

A

TypeScript, Vitest, Testing Library, Playwright with axe

Recommended
  • Vitest + Testing Library: fast checks of pieces such as the fee box, points formatting and the retry key
  • Mock Service Worker plays back the API’s documented answers (422, 409, 429) so every refusal state is tested
  • Playwright runs the core loop in real Chrome and Safari engines at 360 and 768 px; axe fails the build on serious accessibility problems
  • The longest list of build-time packages (none ship to phones)
B

Plain JavaScript, end-to-end tests only

  • Fewer tools to learn
  • Mistakes found later and slower; end-to-end tests alone are slow and flaky
  • KokonutUI and shadcn code would need converting

Why A: the API repo is held to tests, static analysis and style checks on every change; the app should be too. axe in the end-to-end run keeps the U9 accessibility work from slipping.

9

Hosting, deploy and CI

Where the app’s files live, how they get there, and where checks run.

The API runs on one VPS set up with Forge or Ploi (spec §8). The app built under decisions 1–2 is just files, so it can sit on that VPS or on a static host. After the first visit, the service worker serves the app from the phone, so the host’s distance from Dumaguete mostly affects first load; API calls go to the VPS either way. Both repos are on GitHub, and the API already runs GitHub Actions.

A

Same VPS as the API, as a second site

Recommended for the pilot
  • No new account or bill; Forge or Ploi adds the site and a free Let’s Encrypt certificate
  • One place to look when something breaks; keeps decision 4 option C open
  • No CDN: first load comes from the VPS region, not a Manila edge
  • A busy API and the app share one machine (tiny for static files)
B

Cloudflare Pages (static host with a CDN)

  • Free plan; edge servers near the Philippines; preview links for each change
  • Works with decision 4 option A (same parent domain)
  • A third-party account holding the domain’s app address
C

Vercel or Netlify

  • Very easy deploys and previews
  • Their free tiers restrict commercial use or bandwidth; paid sooner than B

Why A: at pilot scale one server is simplest and costs nothing extra; the app is small and cached on the phone. Moving to B later only changes where the files are copied. CI: GitHub Actions in bayanihan-app runs type check, lint, unit tests, build and the Playwright run on every push; deploys only after you merge.

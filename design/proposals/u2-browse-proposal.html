Browse and task detail: choices to make

Eleven numbered decisions for the feed, filters, map, search, the task page someone sees before applying, and public profiles. Each shows the real options as phone screens in the approved U0/U1 style, with a recommendation. Answer by number, or say "all recommended". Nothing here changes U0 or U1. Fake Dumaguete data only; every location shown is an approximate area.

What is fixed

U0 tokens, card, area chip + filter button + list/map toggle, map strip, trust chips, bottom bar, shared states; U1 setup card on Browse until tier 1.

What you decide

The 11 items below. Each has 3 options; the teal-bordered one is recommended. Only feed parameters the API has are used.

After approval

The chosen options become design/u2-browse.html with every state and the endpoints per screen (list below).

The U2 flow

From the Browse tab to a task and its poster. Decision numbers in brackets.

  1. 1Browse list

    U0 cards (D1), area chip, filters (D2), first open (D3).

  2. 2Filters

    Sheet + active chips (D2); Near me asks for location (D3).

  3. 3Map

    Strip or toggle → full map of approximate areas (D4).

  4. 4Search

    Icon → field, when the API has q (D5).

  5. 5Task detail

    Text first (D6), poster row (D7), what you'd receive (D8).

    Chips, bio, reviews (D11).

  8. 8Quiet day

    Widen or post (D10).

How are reviews shown on someone's profile?

GET /users/{ulid}: name, photo, bio, barangay, verified, rating, tasks_done, tasks_posted, member_since. Never phone, legal name, birth date, tier or standing. /users/{ulid}/ratings: newest first, cursor pages, each with stars, comment, role_of_rated and the rater; no task title, no filter by role.

API gaps (new, beyond decisions 0002 and 0003)

Backend work; the mockup will draw these screens but mark the missing data. Still open from before and reused here: barangay list, category list, 429 retry time.

  1. 1. No text search.GET /tasks has no q; spec §5.3 is titled "Browse and search". Needed for decision 5 B or C. Suggest q matched against title and description, combined with the existing filters.
  2. 2. "Tasks done" missing from the poster block.U0 decision 8 shows ID verified, rating and tasks done wherever trust is judged, but poster on the feed and the detail has no tasks_done. Only GET /users/{ulid} has it, so each task opened would need a second request. Suggest adding tasks_done to the shared user block.
  3. 3. Non-posters can't tell "full" from "closed".applications_open: false has no reason for anyone but the poster (applications_closed_reason is poster-only), and the applicant limit (15) is a setting the app can't read. Spec §5.4 wants "Full" shown. Suggest a public applications_closed_reason limited to full / closed.
  4. 4. The map can only show one page.The map uses the feed, which pages at most 50 per request. Fine for the pilot; a city-wide day may need a lighter map query (only ulid, points, approx_location) or a larger page for the map.
  5. 5. Docs: my_application missing from the GET /tasks/{ulid} example.TaskResource returns it to every non-poster (ulid, status), and the button states depend on it, but openapi.yaml doesn't show it. A docs fix, no behaviour change.
  6. Only if 11 = B:a role filter on /users/{ulid}/ratings, plus counts per role.

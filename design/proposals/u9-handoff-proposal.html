Prototype, accessibility pass and handoff: choices to make

U9 turns the nine approved mockups into three things the build (U10) can start from: a click-through prototype of the core loop, an accessibility pass, and a handoff that maps every screen to its endpoints and lists the API gaps in one place. Twelve numbered decisions below, each with options and a recommendation. Answer by number, or say “all recommended”. Fake Dumaguete data, as in U8: Ana R. (Piapi, tier 1) posts “Clean the roof gutter before the rains” for 400 pts; Ben S. (Daro, ID verified, 4.8 · 12) does it.

What is fixed

Every screen, copy and state in design/u0-foundation.html … design/u8-me.html and decisions 0002–0010. U9 adds no new screens; the prototype reuses the approved ones as drawn. Only fields in openapi.yaml.

What you decide

12 items in three parts: prototype (1–6), accessibility (7–9), handoff (10–12). The teal-bordered option is recommended.

Part 1 · The prototype

Decisions 1–6

1

One file or several

How the prototype is packaged, and whether Lavish can open it.

The nine mockups are galleries of frames (role="img" pictures, no real buttons), between 185 KB and 520 KB each. They can’t be clicked through as they are, so the prototype is a new file that redraws the core-loop screens from the approved designs. Lavish opens one HTML file per review.

One file: design/u9-prototype.html

Recommended

+ 6 detours

≈ 30 screens, inline CSS/JS, one Lavish review

  • One link for the owner; one Lavish thread holds every comment
  • Money and status carry across the whole loop, the point of the exercise
  • Bigger file to edit (kept under ~250 KB by sharing one CSS block)
B

One file per flow

u9-proto-signin.html
u9-proto-post-apply-pick.html
u9-proto-work-rate.html
u9-proto-cashout.html

four reviews; balances restart in each file

  • Smaller files, easier to review one at a time
  • The handover between files loses state: Ben’s 380 pts don’t follow him to Cash out
  • CSS copied four times; drift between files

An index linking into the mockups

u9-index.html

  • Not clickable: each link lands on a gallery of frames, not a phone
  • Can’t test keyboard or screen-reader order (decision 8)

Why A: the core loop is about what carries over (points held, status, who sees the pin). Only one file can keep that, and one file is one Lavish review.

Part 2 · Accessibility pass

Decisions 7–9, then a sample of real findings

7

The standard

What “accessible” means for the pass.

A

WCAG 2.2 AA only

WCAG 2.2 AA · 55 criteria

targets ≥ 24 px (2.5.8), text 4.5:1, UI 3:1, 200% resize, reflow at 320 px

  • A known yardstick, matches what a legal review would ask
  • Allows 24 px targets and doesn’t mention Filipino length, both below what our users need outdoors one-handed
B

WCAG 2.2 AA plus our house rules

Recommended
WCAG 2.2 AA
+ House: targets ≥ 44 px (48 for the main action) · body 16 px · Filipino strings +40% · reduced motion · meaning never by color · points read as “400 points, 400 pesos”
  • The house rules are already in CLAUDE.md and the uix skill; this just checks them
  • Each finding says which rule it breaks, so a WCAG pass and a house miss aren’t confused
  • More to check than A
C

Aim for AAA where cheap

AAA text 7:1 · targets 44 px (2.5.5)

teal #0F766E on white is 5.47:1 → fails 7:1

  • Most readable in sunlight
  • The approved teal fails 7:1 on every surface; meeting it reopens decision 0002 #2

Why B: AA is the floor, and our rules (44 px, Filipino length, points read aloud) are where real users in Dumaguete would trip; AAA would undo the approved brand color.

8

How it’s checked

The mockups are pictures; the build will be real elements.

Every phone frame in u0–u8 is role="img" with spans inside: 0 <button> elements across all nine files. A screen reader reads each frame as one picture, and keyboard focus can’t enter it. So the mockups can be audited for what they look like (contrast, size, order, copy length), and the prototype for how they behave.

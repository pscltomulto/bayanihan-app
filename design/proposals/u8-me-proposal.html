The U8 flow

Two doors: the bell, top right on every tab (Me included), and the Me tab. Decision numbers in brackets.

The bell

  1. Count on the bell from meta.unread_count (D2)
  2. List by day, All / Unread (D1)
  3. Tap → marked read → the task, wallet, ID check, standing or a sheet (D2, D3)

Read, unread and the bell

When a notice stops counting, and what the bell shows.

POST /me/notifications/read marks the ids sent (up to 100), or every unread one when ids is left out; it is safe to repeat and returns the new unread_count (60 a minute). The count only comes with the list (0002 gap), so the bell asks for per_page=1 on app start, on return to the app and every 60 s while open; push will refresh it once web push exists.

Recommended

  • A number says how much is waiting; “9+” above nine
  • A cheap extra request for the count (until the 0002 gap closes)

Signed-in devices and “Sign out everywhere”

What the API supports today: this phone, or all of them.

There is no list of sessions or devices: DELETE /auth/token signs out this phone (and its push device); POST /auth/tokens/revoke-all deletes every token and push device, this one included. The new_sign_in notice names the device from the device_name sent at sign-in. The app remembers its own name and sign-in time on the phone, so “This phone” can be shown without the API.

API gaps (new, beyond decisions 0002–0009)

Backend work; the mockup will draw around them. Still open and reused here: a readable 429 retry time, web push subscription and the unread count without the list (0002), the category list (0003).

  1. 1. No list of signed-in phones, and no way to sign out just one. Only DELETE /auth/token (this phone) and POST /auth/tokens/revoke-all (all) exist, so after a lost phone or a strange “New sign-in” the only fix signs out every phone. Suggest GET /auth/tokens (name, created_at, last_used_at, is_current) and DELETE /auth/tokens/{id}.
  2. 2. Push can’t be turned off without signing out. There is no DELETE /me/devices/{token}; a push device is removed only by sign-out or revoke-all. The D4 switch can turn on (once web push exists, 0002 gap) but not off. Suggest a delete by token, and web push (platform: web with a subscription) on POST /me/devices.
  3. 3. No way for a user to close their account. The closed status exists and sign-in then refuses with ACCOUNT_CLOSED, but only staff can set it. Under the Data Privacy Act people should be able to ask for it from the app. Suggest POST /me/close with the rules (no open tasks or disputes; points cashed out or forfeited as the owner decides) and the refusal codes.
  4. 4. Notices are stored in English. Title and body are written at send time in English (e.g. “Standing lowered”), so a Filipino user gets English pushes and the list doesn’t change with the language. Suggest storing a template key and params per notice (the app renders the words), or writing them in the user’s language.
  5. 5. Notices link only to a task. Only task_ulid is sent, so cash_out_paid / cash_out_failed can’t open the U7 status page, cash_in_paid can’t open its cash-in, question_received can’t open the applicant’s thread and dispute notices can’t open the dispute. Suggest a target {type, ulid} (cash_out, cash_in, application, dispute, payout_account).
  6. 6. No notice when a cash-in fails or expires. Spec 5.9 lists “cash-in and cash-out results”, but only cash_in_paid exists. A declined payment is known only if the app is open and polling (U7 D6). Suggest cash_in_failed.
  7. 7. The name can be changed after the ID check. PATCH /me accepts a new display_name at tier 2 and the “ID verified” chip stays, though U1 decision 5 relies on the profile name matching the ID. Owner/backend call: lock the name after approval, or send changes back to review.
  8. 8. The public profile has no skills. GET /users/{ulid} leaves out skills, though spec 5.1 puts skills on the profile. Suggest adding skills {key, label} (D8 option C).
  9. 9. No standing history, and gains are silent. Only drops reach the user (standing_lowered); the +2 per finished task never does, and the notices list has no kind filter to find the last drop. Suggest GET /me/standing with the band and the last few changes, or kind on GET /me/notifications.
  10. 10. Profile edits have no version. Two phones editing at once: the last save wins silently. Low priority; a version or If-Match would allow a 409.

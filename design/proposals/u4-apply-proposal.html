Applying and choosing a worker: choices to make

Twelve numbered decisions for both sides of an open task: the apply form, start time and distance, where applications live, how the poster sees, sorts, stars and questions applicants, the pick, and the ways out (close, cancel, withdraw, drop out), plus reminders. Each shows the real options as phone screens in the approved U0–U3 style, with a recommendation. Answer by number, or say “all recommended”. Fake Dumaguete data; nobody’s standing, phone or exact location appears.

What is fixed

U0 tokens, trust chips, buttons, alerts, sheets and empty states; U2 task detail and its “I can do this” bar states; U3 form fields and photo tiles. Only fields in openapi.yaml (checked against the API code) are used.

What you decide

The 12 items below. Each has 2 or 3 options; the teal-bordered one is recommended.

After approval

The chosen options become design/u4-apply.html with every state and the endpoints per screen (list below).

The U4 flow

Two sides of the same task. Decision numbers in brackets.

Applicant (worker)

  1. Task detail, “I can do this” (U2 bottom bar) → Apply form (D1–D3)
  2. Sent → U2 “You applied” bar and a toast to My tasks › Applied (D4)
  3. Your application: status, what you sent, questions (D8), Withdraw (D11)
  4. Picked → U5 assigned task · Not picked / closed → Closed tab
  5. After the pick, before starting: Drop out (D11)

Poster

  1. New applicant / reminder notice, or My tasks › Posted (D12) → Your task with the applicant list (D5)
  2. Sort and filter (D6), star up to 5 (D7)
  3. Applicant detail: profile, note, past work, questions (D8)
  4. Pick confirm (D9) → U5 assigned task
  5. ⋯ Close applications or Cancel task (D10) · reopen after a drop-out

GET /tasks/{ulid}→POST /tasks/{ulid}/applications→GET /me/applications→GET /tasks/{ulid}/applications→…/messages→…/shortlist→…/accept

1

The apply form

How much room does “I can do this” open?

POST /tasks/{task_ulid}/applications (multipart): earliest_start_at (required, from today to before the deadline), note (≤ 300, phone numbers, links and emails hidden), up to 3 photos (jpg/png/webp, 5 MB), optional lat/lng. U2 put “I can do this” in the detail’s bottom bar. The note keyboard takes half of a 360 px screen.

When can you start?

The API wants a date and time; the spec says “today, tomorrow or a date”.

earliest_start_at is a full time; a time earlier than now counts as now; it must be before the task’s deadline (422 otherwise). Best match gives start time 19%, and posters sort by “Earliest start”, so a too-coarse answer hurts the applicant.

The order already puts better standing first; standing itself is never sent or shown.

7

Shortlisting (stars)

How does a poster narrow down?

POST /applications/{ulid}/shortlist with shortlisted: true|false (send the value, so a retry can’t flip it); at most 5 (meta.max_shortlist), 409 LIMIT_REACHED past that. The applicant never sees the star. Starring or messaging anyone makes an early cancel cost standing (spec §6), so the star is a real commitment.

8

Questions before the pick

Where do the poster and an applicant ask each other something?

GET/POST /applications/{ulid}/messages: up to 3 messages each side (max_questions), ≤ 300 chars, contacts masked by the server; 409 LIMIT_REACHED or INVALID_TRANSITION (“questions close once a worker is picked”), 422 CONTENT_BLOCKED, 30 per hour. The other side gets a question_received notice without the text. Both can still read it after the pick. The applicant uses the same thread from My applications.

9

Picking one worker

How does the poster confirm the pick, and what are they told?

POST /applications/{ulid}/accept: allowed while the task is open, clean and before the deadline (also after closing applications). The task becomes assigned, every other pending applicant gets not_selected, the exact pin goes to the worker, no points move; a repeat answers 200. There is no undo endpoint. Refusals: 409 APPLICATION_NOT_PENDING, WORKER_UNAVAILABLE, DEADLINE_PASSED, TASK_UNDER_REVIEW, INVALID_TRANSITION.

10

Closing applications and cancelling (poster)

Where do the two one-way exits live?

POST /tasks/{task_ulid}/applications/close: no one new can apply, can’t be undone, the poster can still pick. POST /tasks/{task_ulid}/cancel on an open task: every held point returns. Spec §6: cancelling with people still waiting costs the poster −10 standing, unless all of them applied less than an hour ago and nobody was starred or messaged. The app can’t tell which case applies (API gap 1).

11

Withdrawing (applicant) and dropping out (picked worker)

How does a worker step back, before and after being picked?

Before the pick: DELETE /applications/{ulid}, only while pending; no reapply to that task; frees a slot if the task was full; 409 APPLICATION_NOT_PENDING if they were just picked. After the pick, before starting: POST /tasks/{task_ulid}/withdraw with an optional reason only staff see; −10 to the worker’s own standing; the task reopens for the others (third drop-out cancels it). 20 applies and withdrawals per hour.

Already settled (not decisions)

Fixed by the spec, the API or decisions 0002–0005; listed so it can be checked.

Standing stays private

The applicant list comes ordered with better standing first, but no screen shows, names or hints at another person’s standing: no “good standing” label, no rank numbers, and the Best match note lists only rating, experience in the category and start time. A worker’s or poster’s own standing appears only in their own dialogs (drop-out, cancel), marked “only you see it” (0002 #8).

What others see

Applicant cards show only what the list returns: display name, photo, ID verified, rating and count, tasks done, jobs in this category, a distance band, start time, note, past-work photos. Never phone, legal name, birth date, ID images or an exact location. The poster’s exact pin is shared with the picked worker only, after the pick (U5).

Limits shown before they bite

15 applicants (then “Full”), 5 stars (“Starred 2/5”), 3 questions each (“2 of 3 left”), note 300 characters (counter). Rate limits: 20 applies and withdrawals per hour, 30 questions per hour, 60 poster decisions per hour, each with the U0 429 alert and its retry time.

Money

No points move when someone applies or is picked; they were held when the task was posted. The apply form shows what you’d receive (worker_receives); the pick sheet shows held, fee and received; a cancel before the pick returns everything, shown as “400 pts · ₱400”.

Once per task

Withdrawing or dropping out means you can’t apply to that task again (403 RELEASED_FROM_TASK, or the withdrawn application stays). Both dialogs say so before the button.

Push and install

No push prompt after applying or picking (0002 #10.4). The install sheet shows after the first successful application if it hasn’t shown before (0002 #10.3). Every notice also lands in the in-app list.

Past-work photos

Shown through 30-minute signed links. When one expires (403) the app reloads the list once; offline, photos show a grey tile with “Photo needs a connection”.

After a drop-out

The task reopens for the others (at most twice; a third drop-out cancels and refunds). If applications were closed they stay closed. The poster sees how many reopens are left from reopen_count.

API gaps (new, beyond decisions 0002–0005)

Backend work; the mockup will draw around them and mark the missing data. Still open and reused here: a readable 429 retry time (0002), and applicants can’t tell a full task from a closed one (0004).

  1. 1. The poster can’t tell whether cancelling will cost standing. Spec §6 makes an early cancel free only when every waiting applicant applied less than an hour ago and nobody was starred or messaged, but the poster’s task view returns nothing that says which case applies, so the dialog can only say “can lower”. Suggest cancel_lowers_standing (bool) or free_cancel_until on the poster’s GET /tasks/{ulid}.
  2. 2. My applications rows are too thin, and closed tasks can’t be opened. The applicant’s task block has only ulid, title, points, deadline_at: no task status, category (for the icon tile), barangay, worker_receives, applicant_count or poster. Once the task is no longer open, GET /tasks/{ulid} returns 404 to a non-picked applicant, so the row can’t open anything. Suggest those fields in the applicant’s view of the application.
  3. 3. “expired” means three different things to the applicant. An application becomes expired when the deadline passes, when the poster cancels and when staff remove the task. The app can’t word it (“The poster cancelled” vs “No one was picked in time”). Suggest a closed_reason on the applicant’s view (or the task’s cancel_reason in its block).
  4. 4. No unread signal for questions. Rows carry only poster_questions / worker_questions counts, so neither side can mark “new question” on a card or in My applications; the question_received notice is the only cue. Suggest last_question_from and last_question_at (or an unread count) on both views.
  5. 5. Pick reminders aren’t machine-readable. Both reminders use kind pick_reminder with text only; the app can’t tell “24 h after the first applicant” from “6 h before the deadline” to style it or deep-link. Suggest data.reason = applicants_waiting | deadline_soon. Minor.
  6. 6. Apply and application docs are incomplete. openapi.yaml for POST /tasks/{task_ulid}/applications leaves out refusals the code throws: 403 TIER_TOO_LOW, ACCOUNT_SUSPENDED / ACCOUNT_CLOSED, 409 TASK_UNDER_REVIEW, INVALID_TRANSITION, APPLICATIONS_CLOSED with reason accepted, and the two 422 earliest_start_at messages (before today, not before the deadline). GET /applications/{ulid} has no 200 example for either view. Docs only.

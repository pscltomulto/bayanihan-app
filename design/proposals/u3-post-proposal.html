Post a task: choices to make

Eleven numbered decisions for posting a task: the form’s shape, the offer and its fee, the private pin, the deadline, photos, photo proof, the review, low balance, where you land, drafts, and weak signal. Each shows the real options as phone screens in the approved U0–U2 style, with a recommendation. Answer by number, or say "all recommended". Nothing here changes U0, U1 or U2. Fake Dumaguete data; the exact pin appears only on the poster’s own screens.

What is fixed

U0 tokens, buttons, fields, fee box, blocked-post screens, success screen and install sheet; U1 progress bar and upload rows; U2 fee wording. Only fields in openapi.yaml are used.

What you decide

The 11 items below. Each has 2 or 3 options; the teal-bordered one is recommended.

After approval

The chosen options become design/u3-post.html with every state and the endpoints per screen (list below).

The U3 flow

From + to a live task. Decision numbers in brackets.

  1. 0Entry

    + tab or quiet-day "Post a task" → GET /me. Blocked → U0 screen. Draft → resume sheet (D10).

  2. 1What

    Category, title, description, photos (D1, D5).

  3. 2Where

    Exact pin, landmark, house; privacy line (D3).

  4. 3When and points

    Done by (D4), offer with live fee (D2), shortfall (D8), photo proof (D6).

  5. 4Review

    Every answer with Edit, fee box, "Post task · hold 400 pts" (D7).

  6. 5Posting

    Idempotent retry on a weak signal (D11).

  7. 6Success

    Photos sent, held state, install sheet once (D9).

  8. 7Your task

    Hand-off to U4 (applicants, pick).

1

Form shape

One long page, three short steps, or a short form with details tucked away?

POST /tasks needs title (5–60), description (20–1,000), category, points, deadline_at, lat/lng + location_source; optional landmark, address_text, proof_photos_required; photos go up afterwards (up to 4). The map needs most of a screen on a 360 px phone. U1 used one page for the profile because it had five short fields; this form is longer.

2

Points entry and the live fee

How does the poster set the offer, and how is the split shown while typing?

GET /tasks/quote?points= returns fee, worker_receives, available and max_points (1,000 for tier 1, 5,000 for tier 2); minimum offer 50 (limits.task_min). 60 quotes per minute, so the app asks after typing pauses (about 400 ms). The split uses the U0 fee box as drawn in the U0 kit, from the quote, never computed on the phone.

3

Location pin and its privacy

How is the exact spot set, and how do we explain who sees it?

Spec §5.11: the pin defaults to the phone’s GPS and the poster drags to the exact spot; landmark optional; barangay filled from the pin. lat, lng, landmark and address_text are private: only the poster and the accepted worker get them, until 7 days after the job. Everyone else gets approx_location, a 350 m circle the server places. Location permission is asked only here or for Near me.

4

Schedule

How does the poster say when the job must be done?

The API has one time field, deadline_at, between 1 hour and 30 days from now. An open task with nobody picked is cancelled and refunded at the deadline (spec §4). There is no separate "start time" or "flexible" flag, so every option ends in a single "done by" time.

5

Photos

Required or optional, and when are they uploaded?

Photos are optional in the API and can only be added after the task exists: POST /tasks/{task_ulid}/photos, one per request, up to 4, while the task is open, 5 MB each, re-encoded and stripped of GPS data, public with the task. 30 uploads per hour. There is no way to delete a task photo (API gap 2).

8

Not enough points

Where do we catch a low balance, and how do we hand off to adding points?

Posting moves the full offer from available to locked, and fails with 409 INSUFFICIENT_POINTS if available is too low. The quote returns available, so the app knows while you type. Adding points (cash-in) is designed in U7; tier 1 and up; GET /wallet says whether cash-in is open (cash_in.allowed, blocked_reason such as payments_not_live while the fake gateway runs).

Already settled (not decisions)

Behaviour the spec, the API or earlier decisions already fix; listed so it can be checked.

Blocked entry

Tapping + calls GET /me first. When can_post is false the U0 screen for that post_blocked_reason shows before any form (suspended, closed, tier_too_low, dormant_review, reverify_required). A tier-1 account stamped for re-verification still posts, so it gets no screen. If a post is refused anyway (409 ACCOUNT_REVIEW_PENDING, 403 TIER_TOO_LOW or ACCOUNT_SUSPENDED), the same U0 screen replaces the review and the draft is kept.

Idempotency key

A new key is made when the review screen opens and saved with the draft. A retry of the same answers reuses it (no double post). Going back and changing anything makes a new key, because the server matches the replay on title, points, category and deadline only.

Money

Every amount is "400 pts · ₱400". The fee and what your neighbor receives come only from /tasks/quote, before the Post button. The button names what will be held. Points are held, not spent; the copy says "held" and explains the refund before a pick.

Privacy

Only the poster ever sees the exact pin, landmark and house details in this flow; they are marked "Only you". Photos are public, so the hint warns against house numbers and faces. Location is asked for only on step 2 and the GPS fix is never sent anywhere except as the pin you confirm.

Moderation

A blocked word refuses the post (422 CONTENT_BLOCKED, errors.fields): the app returns to step 1 and marks those fields without naming the word, plus a link to the content rules. A review word posts the task as held: points are held and the success screen says it shows in Browse after a check.

Push, install, skills

No push prompt after posting (0002 #10.4). Install sheet after the first successful post only (0002 #10.3). The U1 skills prompt lives on the "you can now post" screen, so it isn’t repeated here.

API gaps (new, beyond decisions 0002–0004)

Backend work; the mockup will draw around them and mark the missing data. Still open from before and reused here: category list, barangay list, 429 retry time.

  1. 1. The open-task limit isn’t visible before the form.can_post / post_blocked_reason don’t cover 409 LIMIT_REACHED (max_open_tasks_per_user, 5), and neither the count nor the limit is readable, so someone with 5 open tasks fills in the whole form before being refused. Suggest open_tasks and max_open_tasks on GET /me (or a sixth post_blocked_reason).
  2. 2. A task photo can’t be removed.Photos can only be added after the task exists and there is no DELETE /tasks/{task_ulid}/photos/{sort}, so a wrong photo stays public until the task is cancelled. Suggest a poster-only delete while the task is open.
  3. 3. No edit after posting.There is no PATCH /tasks/{ulid}, though spec §6 runs the keyword filter "on post and edit". A typo means cancel and repost, which costs −10 standing if applicants are waiting. Decide: edit in V1, or fix the spec wording.
  4. 4. The pin can’t be checked before posting.The barangay (set from the pin) and OUTSIDE_SERVICE_AREA are only known when the post is sent, so the review can’t name the area neighbors will see and an out-of-area pin fails at the last step. Suggest a check that returns the barangay and whether the spot is served for a lat/lng (the barangay list itself is the 0003 gap).
  5. 5. The minimum offer isn’t returned./tasks/quote returns max_points but not the minimum (limits.task_min, 50), so "50 to 1,000 pts" in the hint can go stale. Suggest min_points in the quote.
  6. 6. No notice when a held task is approved or hidden.NotificationKind has no kind for moderation, so a poster whose task was held only finds out by opening My tasks. Suggest a task notice for approved and hidden.

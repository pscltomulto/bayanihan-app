Doing the work and chat: choices to make

Twelve numbered decisions for what happens after the pick: the assigned-task page both sides share, the exact pin and directions, starting, sending proof, the poster checking and confirming, asking for changes, the automatic payment countdown, cancelling by agreement, and the task chat (screen, live updates, after the task ends). Each shows the real options as phone screens in the approved U0–U4 style, with a recommendation. Answer by number, or say “all recommended”. The U5 flow

Status by status, both sides. Decision numbers in brackets.

Worker (“Your job”)

  1. assigned: pin, landmark, Directions (D2–D3); Start sheet with before photos (D4); Chat (D10); ask to cancel or drop out (D9, U4 D11)
  2. in_progress: Send photos of the work (D5)
  3. proof_submitted: “You’re paid automatically by …” (D8)
  4. completed: paid, rate (U6); pin hides after 7 days (D2); chat open until the exact time (D12)
  5. cancelled: points back to the poster; pin and chat closed

Poster (“Your task”)

  1. assigned: waiting for Ben to start; ask to cancel; cancel alone from no_start_cancel_at (D9)
  2. in_progress: started notice, before photos, check-in distance
  3. proof_submitted: check the report, Confirm and pay, or Not quite done? (D6–D7); countdown (D8)
  4. completed: by you or automatically; rate (U6)
  5. disputed: Report a problem → U6

9

Cancelling by agreement

Either side asks; the other accepts or declines; the asker can withdraw.

Assigned and not started only. POST /cancel-request asks; POST /cancel-request/accept (the other side) cancels with a full refund, −10 standing to the poster whoever asked, and the worker loses the pin; DELETE /cancel-request withdraws (asker) or declines (other side), leaves a chat system message and notifies nobody. cancel_request gives requested_by, requested_at and the viewer’s own cooldown_until (12 h; the other side never sees it). The poster alone may also cancel from no_start_cancel_at with no standing change (POST /cancel; earlier → 409 CANCEL_NEEDS_AGREEMENT). The worker’s drop-out is U4 D11.

Live updates and read markers

Messages arrive by Reverb; what happens when the socket drops, and what “read” means.

Who sees the pin

Exact location only on the poster’s and the picked worker’s task view, and for the worker only until it is hidden (7 days after the end, or at once on a cancel or drop-out). Everyone else keeps the 350 m approximate circle. Never in the chat, notices, lists or URLs.

Money

Nothing moves at start or proof. Confirm (or the automatic release) pays worker_receives (400 → 380, fee 20), shown in the confirm sheet as “380 pts · ₱380”. A cancel by agreement returns all 400 pts to the poster.

Standing

Only the poster’s own cancel dialog says “your standing goes down by 10 · only you see it”. The worker’s banner says nothing changes for their standing and never mentions the poster’s. The no-start cancel costs nobody.

Safe retries

Start, proof, confirm, cancel request, accept and decline all answer 200 as they are on a repeat, so the app always offers “Try again” and reuses the same request; nothing can pay or report twice.

Start, proof, confirm and the cancel-request calls share 30 per hour; chat 30 texts per minute and 20 photos per hour; read markers 120 per minute; 4 photos (5 MB) at start and at proof; note 300, message 1,000 characters (counters). Each 429 uses the U0 alert with its retry time.

API gaps (new, beyond decisions 0002–0006)

Backend work; the mockup will draw around them and mark the missing data. Still open and reused here: a readable 429 retry time (0002), and no tasks_done on the person block (0004), so trust chips show ID verified and rating only.

  1. 1. No request-changes step. The brief asks for “confirm or request changes”, but spec §4 and the API only allow Confirm, waiting for the 24 h auto-release, or Report a problem (a dispute). The worker can’t resend proof (a second /proof returns the task unchanged) and nothing pauses auto_release_at. Needs an owner/spec decision; if wanted: a changes_requested status, POST /tasks/{ulid}/request-changes with a note, a resubmit, and a cap on rounds.
  2. 2. No read receipts. POST /messages/read moves only your own marker; the other side’s marker isn’t in meta and no read event is broadcast, so “Seen” can’t be shown. Suggest meta.other_read_up_to and a message.read broadcast, if the owner wants Seen (D11 option B).
  3. 3. Task status changes aren’t broadcast. The only Reverb event is message.sent. Start, proof, confirm, auto-release and cancel requests reach an open task page only through their system chat line (and only if those are written for every change), so the app refetches the task on any system message and on focus. Suggest a task.updated event (status, version) on the same channel.
  4. 4. The worker can’t tell when the pin will hide. location just stops being sent; hidden_at isn’t returned and the 7-day rule isn’t readable, so “The exact spot locks on Fri 4 Dec, 9:40 AM” can’t be shown reliably. Suggest location_hidden_at on the worker’s (and poster’s) task view.
  5. 5. My tasks / My jobs rows are too thin for work in progress. GET /me/tasks and /me/jobs cards carry status but no worker/poster name, auto_release_at, chat unread_count, pending cancel_request or “your move” flag, so the list can’t show “Confirm by Fri 9:40 AM”, unread messages or a waiting cancel request. Suggest those fields on the active cards.
  6. 6. Chat 429s don’t say which limit. Text (30/min) and photo (20/hour) limits both answer TOO_MANY_REQUESTS; the app can’t say “photos: try again in 40 min” vs “try again in 38 s”. Suggest errors.limit = chat_messages | chat_images with the retry time (the readable 429 retry time is still open from 0002).
  7. 7. A declined cancel request notifies nobody. DELETE /cancel-request by the other side leaves only a chat system line; the asker gets no push, so they may wait for an answer that already came. Suggest a cancel_request_declined notice to the asker. Minor.
  8. 8. Before photos only at start. Before photos can be sent only with /start; a worker who forgets or whose camera fails can’t add them. Acceptable for V1 if the start sheet asks (D4); otherwise a POST …/work-photos/before while in_progress. Minor.
  9. 9. Docs: the assigned task view isn’t documented. The GET /tasks/{ulid} example in openapi.yaml shows only the public view; location (with landmark, address_text), worker, work, checkin, cancel_request, no_start_cancel_at, chat_channel, dispute and rating are missing. The message examples leave out type; CLAUDE.md names the channel task.{ulid} while the code uses task.{ulid}.{worker_ulid}. Docs only.
